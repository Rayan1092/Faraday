# NV: one-command Mac launcher (2026-11-15 02:30)

Owner item 2: `integration/start_mac.sh` gets everything up, checks it all and starts Faraday with `--fresh`.

## What it does, in order

Every step prints one wide `[ OK ]`, `[WARN]` or `[FAIL]` line, readable from across the table.

1. Creates `config/settings.json` from the example if it's missing.
2. Checks that Wi-Fi is off.
3. **LM Studio:** waits up to 30 s for its server. If the `lms` CLI is installed, it starts the server with `lms server start`, and loads the profile's 9B and 2B with `lms load`. Then both must be downloaded AND loaded; anything else loaded gets an eject warning.
4. **Argmax STT:** if `argmax-cli serve` isn't answering, the launcher starts it itself in the background, logging to `cache/argmax-serve.log`, and waits up to 120 s for an answer. If it never comes up, the FAIL line shows the log's last lines.
   - The command is `stt.mac.serve_command` if set (a list or a string). Otherwise it is plain `argmax-cli serve` (the binary from `tts.mac.command`), the known-working command, plus `--port` only when it isn't 50060.
   - The flags `--port`, `--host` and `--model` are confirmed in `Sources/ArgmaxCLI/Server/ServeCLIArguments.swift`.
5. **The rest:** the TTS binary, the object detection model, OpenCV 4.7+, the default mic and speaker (names printed), the camera (one frame, size printed), the Flipper port, the example passphrase, and whether the owner voice is enrolled.
6. **Verdict:** a READY banner (counts) and then `python3 -m integration --fresh <args>`. Or a NOT READY banner listing every FAIL, and nothing starts.
   - `--no-fresh` keeps the old log and captures.
   - `FARADAY_SKIP_CHECKS=1` starts anyway.
   - `FARADAY_DRY_RUN=1` checks only.

macOS ships bash 3.2, so the script avoids newer bash features (empty-array expansion under `set -u`).

## Tests

`integration/tests/test_start_mac.py`, 14 tests:
- the launcher starts a stand-in `argmax-cli serve` itself and waits for it
- a serve that dies gives NOT READY with its log
- `--fresh` by default; `--no-fresh` keeps the old log
- the existing model and STT checks

The tests set `FARADAY_DEVICE_CHECKS=0` and `FARADAY_USE_LMS=0`, so they never probe a mic or camera or drive a real LM Studio. An early run did reach this laptop's real `lms`: LM Studio's server is running on the NV laptop now, with no model loaded.

`docs/team/history/MAC_TEST.md` is updated: one command in step 8, and the owner voice steps 17-19.

## Review (fresh reviewer agent) and fixes

- **Tests and a real serve:** the tests could start a real `argmax-cli serve` (on the Mac: large-v3 loading on port 9, never killed). `FARADAY_START_STT=0` now stops that, and the tests set it, as they set `FARADAY_USE_LMS=0` and `FARADAY_DEVICE_CHECKS=0`.
- **Serve that dies:** a serve that died at once still cost 120 s. On the Mac the launcher now notices and FAILs at once. It won't start a second copy if one is already loading (`pgrep`), and on timeout it says "may still be loading, run it again".
- **Real seconds:** the waits count real seconds (`$SECONDS`), not loop turns with curl timeouts.
- **Detached serve:** it's started by a small Python `Popen(start_new_session=True)`, so the pid printed is argmax-cli's own and Ctrl-C on the app doesn't stop STT.
- **`lms`:** used only for models that are already downloaded, with a time limit (`perl alarm`; macOS has no `timeout`), and no interactive fallback. `lms server start` has a time limit too.
- **Device check:** uses `audio.mic_device` and `audio.speaker_device`, gives the camera 5 warm-up reads, runs unbuffered, and WARNs if it can't run.
- **Small ones:** a string `serve_command` is split properly, "voice check on" is printed only when a diarize command exists, and the FAIL list no longer interprets backslashes.
- **MAC_TEST.md:** step 6 is now `FARADAY_DRY_RUN=1 integration/start_mac.sh`, which brings LM Studio and STT up for step 7's camera/vision checks. The `serve_command` note includes `pkill -f "argmax-cli serve"`.
